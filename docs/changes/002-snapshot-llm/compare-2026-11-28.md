### openai

Tools: `read_file docs/decisions-log.md`, `read_file docs/spec.md`, `read_file src/tinykv/store.py`, `read_file sessions/2026-10-01-planning.md`

Tiny-kv uses an append-only log to avoid rewriting all existing data on every `put`: the planning notes contrast that with a JSON file rewrite, which would require O(n) writes and be unsafe on a crash. With the log, a torn write can lose the last record, and its CRC helps detect that damage (planning notes; KV-D1).

The tradeoff is controlled with compaction: the spec calls for rewriting live records once the log exceeds 4× live data size, then replacing the log via rename (KV-D3; `docs/spec.md:11-13`).

### anthropic

Tools: `read_file docs/decisions-log.md`, `search_files append`, `read_file sessions/2026-10-01-planning.md`

The project chose an append-only log for crash safety, and it avoids rewriting the whole file on every write.

- **Crash safety:** KV-D1 says a torn write only loses the last record, and the CRC detects it (`docs/decisions-log.md:5`). Rewriting in place can corrupt the whole file if a crash happens mid-write.
- **Write cost:** The planning session compared a JSON file rewritten on every `put` (simple, but O(n) writes and unsafe on crash) with an append-only log (O(1) writes, crash-safe with a CRC). The team chose the log (`sessions/2026-10-01-planning.md:4-7`).
- **Dependencies:** The same session notes that SQLite was considered and set aside because the brief asked for no dependencies (`sessions/2026-10-01-planning.md:3-4`).

The design is in `docs/spec.md:11`, and the commit is `1a0c5e2` ("Append-only log with CRC (KV-D1)", `git-log.md:5`).

The trade-off is that the log grows with every write. That's why KV-D3 and requirement K3 call for compaction once the file exceeds 4x the live data size (`docs/decisions-log.md:7`, `docs/spec.md:8`).

I didn't read `src/tinykv/store.py` beyond its module docstring, so I haven't checked the implementation against this design.

## Q3. Is compaction implemented, and what does the code actually do today?

| Provider | Model | Latency | Tool calls | LLM calls | Input (cached) | Output | Cap hit |

| openai | `gpt-6-luna` | 8.8s | 4 | 2 | 3397 (2464) | 1053 | false |

### openai

Tools: `read_file src/tinykv/store.py`, `read_file tests/test_store.py`, `read_file docs/spec.md`, `read_file sessions/2026-10-03-build.md`

**No—compaction is not implemented.** `put` checks the threshold and calls `compact()` inline, but `compact()` only sets a `.tmp` path and raises `NotImplementedError`; it doesn’t rewrite records or rename a file (`src/tinykv/store.py:17-27,39-42`).

The check also doesn’t measure live data: `live_bytes` increases by every appended record and is never reduced when a key is overwritten (`src/tinykv/store.py:24-27`). On a new store, it therefore tracks the appended file bytes, so the `file size > 4 × live_bytes` condition won’t be reached through ordinary puts. If the condition is reached, the record has already been written, flushed, and fsynced before the exception is raised (`src/tinykv/store.py:20-27`).

That differs from the spec’s K3 requirement and rewrite-and-rename design (`docs/spec.md:5-7,11-13`), and from the build note saying compaction runs inline (`sessions/2026-10-03-build.md:4-5`).

### anthropic

Tools: `read_file src/tinykv/store.py`, `search_files compact`, `read_file sessions/2026-10-03-build.md`

**No. Compaction is not implemented.** The threshold check exists, but the method it calls is a stub that always raises.

- `src/tinykv/store.py:26-27`: `put` calls `self.compact()` once the file size exceeds `COMPACT_RATIO * live_bytes` (4x, tied to KV-D3).
- `src/tinykv/store.py:39-42`: `compact()` sets a `tmp` path, then raises `NotImplementedError("compaction lands in v1.1")`. It never rewrites live records or renames `data.log.tmp` over `data.log`.

So once a store's file passes the threshold, the next `put` raises after it has already written and fsynced the record. Nothing in the snapshot catches this.

The docs describe more than the code does:
- `docs/decisions-log.md` KV-D3 records the decision (rewrite-and-rename, triggered at 4x live size).
- `docs/spec.md:12` describes the compaction design, and K3 (`docs/spec.md`) requires the file never to exceed 4x live size. The code does not meet K3 today.
- `sessions/2026-10-03-build.md:4-5` says compaction "runs inline in `put`", which describes the intent, not the current code.
- `git-log.md:3` shows commit `3f2a1c9` "Add compaction threshold (KV-D3)". That commit added the trigger, not the rewrite.

I also see a possible accounting problem. `put` adds every record's length to `live_bytes` (`store.py:25`) and never subtracts the superseded record when a key is overwritten. So `live_bytes` tracks bytes written, not live data, and the trigger may fire later than KV-D3 intends. I did not verify this by running the code. The `_load` method (`store.py:44-46`) is shown only partly, so I can't confirm whether it restores `live_bytes` at startup.

I found no compaction tests in the search results. `tests/test_store.py` was not read.
